## One selected boundary and reconciliation decision

V0.58 freezes exactly one repository-supported boundary: **Core-owned Worker
Activation Runtime Interface Prerequisite evidence**, as implemented by v0.57.
The only interface-stage success marker remains
`worker_activation_runtime_interface_prerequisite_recorded`. It means a fixed
inventory was recorded for one exact active same-owner review. It never means
prerequisites satisfied, interface defined, contact authorized or worker-start
admitted. V0.58 creates no additional admission marker, schema, ID/hash domain,
store, permission, API route or UI consumer.

The original P0 required deferral if admission merely repeated inventory validity.
The integrated `evaluate_worker_activation_runtime_interface_prerequisite` already
validates exact lineage, scope, authority, freshness, reservation facts and the
complete fixed inventory; success recognizes one v0.56 review, refusal zero with
an empty inventory and false marker. Closed record/status validators also enforce
the exact inventory. P0's proposed v0.58 acceptance of inventory completeness
supplies no additional predicate or proven consumer need. There is no repository
consumer requiring a second persisted acceptance. Accordingly **P1-P5 are deferred**,
not silently authorized by this freeze. A future distinct boundary needs a new
normative decision, consumer justification, vectors and feasibility evidence.
Runtime interfaces or effects cannot substitute for the redundant evidence stage.

## Exact lineage, time and durability

Retain complete immutable pairs recursively: v0.57 inventory -> v0.56 review ->
v0.55 plan -> v0.54 runtime admission -> v0.53 runtime prerequisite -> v0.52
queue receipt -> v0.51 acknowledgement admission -> v0.50 acknowledgement
prerequisite -> v0.49 claim admission -> every inherited v0.48-v0.20 pair in the
[v0.55 lineage contract](worker-activation-runtime-plan-v1.md#closed-plan-and-exact-v054-prerequisite-lineage).
All owners, candidate/abstract subjects, IDs, times, limits and version-specific
fingerprints remain exact. The v0.52 receipt records injected already-observed
assertions; Core did not perform or independently verify those queue effects.
It grants no queue primitive.

Reparse strict closed models after copy/construct bypass, reject extra/duplicate
fields and coercion, and validate each version with its own hashes and IDs.
V0.57's durable reader obtains v0.56 by exact owner/candidate/review ID, checks
current eligibility using trusted whole-second UTC Core time, and derives stable
v0.56 status at review `recorded_at`. Create pins that stable status fingerprint,
review fingerprint, review ID and exact expiry. No caller-supplied nested evidence,
latest fallback, foreign owner, alternate subject or worker lookup is accepted.

The existing v0.57 store supports exact owner/candidate/prerequisite-ID `get`.
V0.57 service item GET derives status at trusted current time; list GET returns
records without paired statuses. Neither creates a durable successor reader.
Any separately approved future successor would need a new owner-scoped reader,
stable v0.57 status at inventory `recorded_at`, and independent current eligibility
checks. An arbitrary item-GET status fingerprint cannot be assumed stable.

Record lifecycle remains `active`; status becomes `expired` at
`evaluated_at >= valid_until`, retaining the inventory, blockers, eligibility
literal and recorded markers. A true historical marker does not prove current
eligibility. Reject future time, stale evidence over 30 seconds and expiry at
`now >= valid_until`. Preserve every nested historical validation time and the
inherited exact expiry; never normalize time, truncate lineage or renew freshness.

V0.57 revalidates predecessor/time under both journal write locks, reserves
owner/key and permanent subject before append, and leaves ambiguous reservations
terminal. Exact duplicates preserve the record without predecessor reads or
renewal (response status still reflects current time). New keys/expiry/content
cannot replace a subject, even after restart or expiry. No repair, retry, replay,
eviction or predecessor journal mutation is authorized. Ceilings remain 16
reservations per owner, 256 globally (including incomplete reservations), one
terminal audit per reservation, 192 KiB per full model/response and 256 MiB main
SQLite database pages, not a filesystem quota. Limits may decrease, never expand.
No additional v0.58 embedding has been measured or authorized.

## Frozen API surface

The existing base is
`/api/v1/installation/candidate-records/{candidate_record_id}/worker-activation-runtime-interface-prerequisites`.
Exactly POST/list GET exist there; item GET appends
`/{runtime_interface_prerequisite_id}`. POST returns the exact result pair with
201 including exact duplicates; list returns the collection; item GET returns
the record/status result. Create pins `runtime_plan_review_id`,
`runtime_plan_review_record_fingerprint`, predecessor `status_fingerprint`,
`valid_until`, and
`requested_scope=worker_activation_runtime_interface_prerequisite_only`, plus
schema/authority constants. Authentication owns operator identity and the route
owns candidate scope. Inventory is fixed by Core, never supplied by the caller.

Permissions are
`installation.execution.worker_activation_runtime_interface_prerequisite.evaluate`
and `.read`. POST requires trusted Origin/CSRF, one 16-128 visible ASCII
Idempotency-Key and strict JSON bounded to 16 KiB/nesting 16. No queries or GET
bodies are accepted. Responses are reparsed and bound to owner/candidate, item ID
or create pins/key. Collection maximum is 16 within the full 192 KiB bound.
Missing service is 503, disabled creation 409, foreign/missing 404;
authentication/permission/throttle failures are 401/403/429, malformed/oversized/
wrong-content-type requests 422/413/415. Errors are redacted and non-retryable.
There is no v0.58 API addition, enabling setting or runtime route.
