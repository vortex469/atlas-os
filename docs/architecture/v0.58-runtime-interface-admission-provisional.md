## Candidate decision and distinct value gate

The likely next narrow boundary is **Worker Activation Runtime Interface
Admission evidence**: Core could accept one exact active same-owner v0.57
prerequisite inventory solely for separately contracted future interface design
consideration. The tentative marker
`worker_activation_runtime_interface_admission_recorded` would mean only that
this bounded evidence decision was recorded. It would never mean interface
prerequisites satisfied, interface defined, contact admitted or worker-start
admitted. No marker or API is created by P0.

The conditional distinction is that v0.57 proposes a blocker-to-owner/proof
inventory; v0.58 could bind a deterministic acceptance/refusal decision to one
exact inventory after checking its frozen completeness and scope. Completeness
means every required inventory entry is present, not that its proof obligations
have been discharged. Success recognizes exactly one predecessor; refusal
recognizes zero and leaves the new marker false. Neither result removes a blocker.

This is an architectural inference, not a successor authorized by release
numbering. A2 must establish a concrete consumer need for persisted acceptance
and a predicate distinct from v0.57's own validation. If v0.57 already makes that
decision, or a new record merely restates inventory validity, **defer P1-P5 and
retain this document only**. No extra review layer is justified by sequence alone.
Interface specification, runtime/store adapters and worker-start admission would
require identity, authentication, bounded effects and recovery contracts absent
from the inspected chain; they cannot substitute for a redundant evidence step.
