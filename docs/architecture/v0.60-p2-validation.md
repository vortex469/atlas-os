# v0.60 P2 — retained durable evidence store hardening

The [synchronized boundary](v0.60-runtime-definition-boundary.md) and
[P1 implementation evidence](v0.60-p1-validation.md) retain the Core-owned
v0.57 prerequisite service/store integrated through v0.59. There is no distinct
v0.59 evidence pair or approved v0.60 successor schema. This P2 request hardens
that existing production store; it does not invent a definition journal or
truncate the exact v0.56 predecessor lineage.

The retained implementation already provides owner-scoped reads, permanent
subject and owner/key reservations, exact duplicate readback, two locked
predecessor validations, terminal uncertainty, restart durability and lower-only
retention limits. Creation remains default-off and evidence carries the same
blocked authority. No Agent, worker, execution or production construction
surface changes.

## Implementation

Schema metadata was previously fetched into Python before exact schema
comparison. Corrupt metadata could therefore bypass the journal's bounded cell
readback policy. The store now preflights schema row count, name and SQL storage
types, and UTF-8 byte lengths inside SQLite before materializing metadata, both
on construction and every live transaction. Limits derive from the fixed trusted
in-memory schema. SQLite's legitimate NULL autoindex SQL remains accepted; the
subsequent exact schema comparison remains mandatory. Corruption returns only
`store_corrupt`, without repair, eviction or database mutation.

These limits bound Python metadata readback, not SQLite's internal schema parsing
or total process memory. The existing database page ceiling remains a page
bound, not a filesystem quota.

## Validation

multibyte SQL with a permitted character count but excessive byte count, and
successful restart with the exact schema. A guarded SQLite connection fails the
test if hostile metadata reaches the raw Python readback query. Live list,
idempotency lookup and restart must return redacted corruption errors and leave
the journal byte-identical.

`test_release_closure.py` suites for ownership, lineage at both write locks,
