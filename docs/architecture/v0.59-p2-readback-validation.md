# v0.59 P2 — exact create readback closure

The synchronized [v0.59 freeze](v0.59-runtime-interface-boundary.md) retains
the existing bounded durable prerequisite service/store and the integrated
v0.58 hardening. A new successor journal or synthetic v0.58 predecessor pair
remains deferred. The durable predecessor is the same-owner v0.56 review and
its stable status, with current eligibility checked under both write locks.

This follow-up closes create response validation at the service boundary.
Both the initial idempotency lookup and append readback now strictly reparse
the returned record and independently bind it to the authenticated owner,
candidate, owner/key fingerprint and complete create pins. This also covers
a competing append that resolves to an exact duplicate. A valid but mismatched
record produces a redacted, non-retryable fingerprint error; forged models
remain closed by strict validation.

Readback validation uses the retained embedded predecessor pair. It performs
no predecessor reads, freshness renewal, additional journal writes or runtime
effects. Permanent reservations, bounded retention, interrupted-append closure,
default-off construction and the downstream authority ceiling remain intact.

The focused regressions exercise all three readback paths with valid records,
foreign owner/candidate/key, alternate predecessor ID/record/status pins,
changed expiry and copy-forged authority. Existing focused cases cover restart
and expired duplicates, permanent subject replay refusal, corruption preflight,
both SQLite write locks, deterministic in-flight competitors and default-off
behavior. Separate static closure checks pin the production consumer inventory
and retained v0.58/v0.59 authority boundary.
