# Codex Execution Sandbox Hardening

Atlas runs approved Codex mutations in a disposable repository clone inside the
`atlas-execution-worker` container. The worker uses the `runsc` runtime as uid
`10001`, a read-only root filesystem, `CapDrop=ALL`, and
`no-new-privileges`. The immutable execution argv selects the named
`atlas-workspace` Codex permission profile, which extends Codex's built-in
`:workspace` policy and permits network access without weakening filesystem
confinement.

Network-enabled model commands share the worker's outer network namespace. The
production topology therefore separates the control plane from egress:

- Agent and `atlas-execution-worker-relay` share the internal transport network.
- Worker, relay, and the pinned Squid proxy share the internal worker network.
- The relay listens only on its transport-network address.
- The worker accepts execution and result requests only from the relay's fixed
  worker-network address and with a persistent random bearer token.
- The token is generated by a one-shot, capability-limited staging service and
  mounted read-only into Agent and worker. It is not included in model argv or
  environment.

The container release gate creates an isolated stack and runs a disposable
Codex sandbox proof. The proof must write inside its workspace, fail to mutate
worker state outside the workspace, and receive `403 untrusted_peer` when it
uses the mounted token to contact the worker directly. The gate also verifies
that the worker cannot reach the relay listener and that Agent health traffic
reaches the worker through the relay.

Atlas Agent remains the sole workflow, approval, verification, review, patch
application, and commit authority. Worker execution stays disabled by default;
enabling it remains an explicit production setting.
