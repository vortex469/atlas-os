## Decision in one sentence

The minimum controlled runtime activation boundary is not “start a worker” and
not another consistency receipt: it is a separately authenticated, one-shot,
owner-bound authorization envelope that binds one reviewed runtime declaration
and one immutable artifact to fixed capability/resource/network/filesystem
limits, then records a durable terminal outcome without itself performing the
runtime effect. Even this boundary remains a conditional research target until
its provenance, contact and effect semantics are proven.

## The minimum boundary

The smallest useful controlled boundary has two deliberately separate planes:

| Plane | Minimum responsibility | Explicit non-responsibility |
| --- | --- | --- |
| **Control plane** | Authenticate the operator and candidate, verify one exact reviewed declaration and artifact digest, enforce fixed policy limits, reserve a single-use activation capability, and persist a terminal accepted/refused/uncertain result. | Does not create a process, pull an image, mount a path, contact a worker store, or invoke an Agent. |
| **Effect plane** | A separately owned runtime adapter may consume the capability, authenticate the exact subject, enforce the same immutable limits, and report a bounded effect result. | Is not implied by a control-plane receipt; it cannot infer permission from UI state, health, queue state, or a latest-record lookup. |

The boundary is minimum only if removing any one of these controls makes the
decision ambient, replayable, substitutable, or unable to explain uncertainty:

1. **Exact subject binding:** authenticated `operator_id`, installation or
   candidate identity, and one exact runtime declaration/version. No nested
   caller-supplied authority, latest lookup, or foreign-owner substitution.
2. **Immutable execution input:** an accepted artifact digest plus a reviewed
   runtime identity, capability set, resource limits, filesystem policy and
   network policy. Mutable tags, ambient host configuration and unbounded
   inherited environment are not acceptable inputs.
3. **Single-use authorization:** an explicit activation identifier, expiry and
   idempotency/replay rule. Reservation must precede any effect; retries must
   converge to the recorded terminal result and never create a second start.
4. **Authenticated contact:** the effect-plane adapter must prove the exact
   authorized subject and permitted operation. A queue, database, HTTP route or
   execution-worker ledger cannot substitute for this contract.
5. **Bounded outcome:** accepted, refused and indeterminate outcomes must be
   distinguishable and durable. Indeterminate means “do not retry blindly”; it
   cannot be presented as readiness or successful start.
6. **Revocation and recovery:** expiry, operator cancellation, adapter loss,
   restart and partial completion need explicit semantics. Recovery must not
   replay an unknown effect or silently widen policy.

This decomposition is a design test, not a selected schema. The exact names,
IDs, hash domains, storage owner and API surface require a later normative
contract.

## Gates before selecting even the minimum boundary

All gates are open and no P1-P5 work is authorized by this P0.

1. **Accepted baseline:** pin the integrated predecessor and resolve its
   independent Core, worker and release obligations. A focused regression pass
   is not release acceptance.
2. **Distinct trusted decision:** provide consistent and conflicting test
   declarations over the same exact artifact/inventory input; identify the
   trusted author, deterministic policy source, refusal semantics and the
   concrete consumer decision that differs from retained evidence.
3. **Exact approval relationship:** define who may authorize activation,
   whether approval is candidate-, artifact- and policy-bound, and how
   cancellation, expiry, supersession and ownership transfer behave.
4. **Runtime and contact contract:** specify the authenticated subject,
   operation vocabulary, credential boundary, allowed effects, adapter
   capabilities and failure/uncertainty behavior. Do not derive these from
   the Core evidence journal or execution-worker ledger.
5. **Measured immutable limits:** pin artifact digest, runtime identity,
   capabilities, CPU/memory/PID limits, writable paths, mounts, environment,
   DNS/ports and other resource bounds. Reject mutable tags, extra fields,
   coercion, ambient inheritance and policy widening.
6. **Durable one-shot proof:** establish reservation-before-effect,
   restart/no-replay, concurrency, corruption, expiry, terminal uncertainty,
   redacted failures and recovery without predecessor mutation. Measure storage
   and response bounds before selecting domains or migrations.
7. **No authority promotion:** missing contact proof, stale or foreign status,
   forged lineage, adapter timeout, ambiguous result, queue visibility,
   dashboard state and health checks must remain non-authorizing.

Failure of any gate keeps successor P1-P5 deferred. A proposal that crosses
from authorization into process/container creation, store contact, Agent
invocation or execution needs a separate authority decision rather than being
smuggled into this minimum boundary.

## Conditional reopening shape

If the gates later pass, a separately approved successor should be staged as a
reference-only control-plane contract first: pure evaluator and vectors, exact
owned predecessor reader, default-off durable reservation, guarded evidence API,
then nested GET-only presentation and closure isolation. Only a later decision
could authorize a separately owned effect-plane adapter. P1-P5 are therefore
conditional responsibilities, not a roadmap commitment or implementation plan.
